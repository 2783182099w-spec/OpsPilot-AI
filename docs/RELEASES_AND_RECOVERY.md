# 发布、诊断和自愈

## 发布流水线

由 CI 构建制品并计算 SHA-256。管理员通过发布页或 JWT API 提交应用标识、制品版本、无凭据的 HTTPS URL、校验值、目标主机和变更原因。API `POST /mtask/releases` 第一次返回签名预览。第二次发送相同数据、预览的 `token` 和 `confirmed: true`，生成待审批任务。预览有效期十分钟，主机连接、环境、应用策略或提交内容变化后需重新生成。

可在发布页点「发布指引」查看首次接入步骤、demo-web 参数案例和可复制的 Linux CI 模板。管理员从「发布流水线 → 应用与 CI → 登记应用」选择 CMDB 中的 Linux 主机，填写 systemd 单元、可信 HTTPS 来源和健康检查参数。保存立即生效。登记后可点击「发布预检」，通过 SSH 检查最多 20 台主机的目录、当前账号写入权限和 systemd 配置，在任务中心查看结果。预检不会创建发布目录或重启服务。

旧环境变量 `OPSPILOT_RELEASE_TARGETS` 仍可作为配置来源。同名平台登记优先，停用平台登记后该应用停止接受发布及 CI 上报。下例里的应用、主机 ID、来源与健康接口均是占位示例。

```json
{
  "demo-web": {
    "unit": "demo-web.service",
    "host_ids": [101, 102],
    "environment": "test",
    "origin": "https://artifacts.example.test",
    "port": 8080,
    "path": "/health"
  }
}
```

目标需预置 Python 3、Bash、GNU coreutils 与 systemd。运维账号需要写入 `/opt/opspilot-releases/demo-web/` 并管理指定单元。单元需预先加载，`ExecStart` 直接指向该目录下的 `current`。限制目录权限，只允许受信任账号写入。制品必须是适用于目标主机的单文件可执行程序，目标机器须能连接配置的 HTTPS 来源。下载限制 100 MiB，拒绝重定向并验证 TLS 和 SHA-256。制品按摘要保存，切换 `current` 符号链接后重启服务并连续三次验证本机 HTTP 健康接口。

另一名管理员批准后，先派发一台。首批验证通过后等待独立管理员放行，后续每批最多四台，并发最多两台，达到一台失败停止派发。已经派发的主机可能仍在执行，处理时以任务结果中的逐台阶段和“可能已执行”记录为准。回退由管理员从较新的发布记录发起，目标版本须曾在所有选中主机验证成功，同样需要审批与健康验证。制品仓库需要保留回退版本，目标机需按容量和保留策略清理旧制品。数据库迁移等外部状态需使用独立恢复流程。


发布工作台支持按应用、版本、提交人和状态筛选。发布详情可查看当前阶段、审批和放行人、逐台执行证据。独立管理员可在详情内批准、驳回或核对首批后放行。预览可以指定首批主机；同一应用的版本号提交后绑定制品摘要。回退选项由服务端计算，候选版本仅列出曾验证成功、未被后续发布覆盖且仍在白名单内的主机。管理员变更应用策略后，旧任务须重新预览。


## 从 CI 登记制品

1. 在「应用与 CI」打开应用的「CI 接入」，生成应用专用令牌，将令牌保存为 CI 密钥 `OPSPILOT_CI_TOKEN`。页面只显示一次。通过 HTTPS 或受控本机回环访问平台接口。
2. CI 将单文件 Linux 制品上传到已配置的 HTTPS 来源。创建 `artifact.json`，填写版本、完整下载地址和小写 SHA-256。
3. 用下面的命令登记制品。将 `OPSPILOT_URL` 配置为 CI 可以访问的 OpsPilot 后端基址，部署通过反向代理时包含实际 API 前缀。

```sh
curl --fail --silent --show-error -X POST "$OPSPILOT_URL/mtask/ci/demo-web/artifacts" \
  -H "X-OpsPilot-CI-Token: $OPSPILOT_CI_TOKEN" \
  -H "Content-Type: application/json" \
  --data-binary @artifact.json
```

4. 运维管理员从发布页选择上报的制品，核对目标和首批主机，提交审批。重复发送相同清单可安全重试，同一版本的清单发生变化会被拒绝。

## 诊断与自愈

Prometheus 和 Node Exporter 继续负责主机指标。服务健康由监控同步器额外探测授权资产的登记 IP、HTTP 端口与路径。每轮最多并发四个探测，最多配置 32 个端点。连续三次失败才触发告警，连续三次通过才记录恢复。探测不跟随重定向，禁止使用回环、链路本地地址等敏感目标。停用和维护中的资产显示未知，旧数据不用于判断恢复。

运维员从「告警中心」打开详情，可执行平台按告警来源匹配的只读排查。巡检重跑原检查项；磁盘和 inode 会定位高占用挂载点；采集失联与采集器异常由 Prometheus 侧核对。缺少可匹配依据时，页面提示手动选择模板。管理员在「诊断策略」编辑分支和结论。HTTP 探测策略可留空模板并使用内置检查。内置检查有本机 HTTP、TCP、systemd、磁盘和日志关键词。每个检查须配置通过、异常和待确认分支；循环、悬空引用和不可达节点会被拒绝。可在授权主机试跑，也可在告警中查看绑定的诊断和修复任务。执行任务持有当时的模板版本和定义，日志关键词检查只输出匹配计数。

HTTP 探测策略可选仅监控、自动诊断、提交人工审批的修复、测试环境自动修复。修复前必须已完成本轮诊断。人工修复由另一名管理员审批。自动修复需同时设置 `OPSPILOT_AUTOMATIC_REPAIR=1` 并在对应测试资产策略选中自动修复。当前内置动作仅支持 `nginx.service`。同一告警轮次最多一次修复，同一主机设 30 分钟冷却。维护状态、过期采样、已恢复告警、配置变更及同服务发布会阻止派发。脚本复核本机连接被拒、systemd 单元确已失败、结果为退出码错误和 `nginx -t` 成功后，最多启动一次并复检。服务告警恢复由后续连续探测确认。告警详情可授权「仅本次自动处理」，授权绑定本轮告警且不修改持续策略。诊断策略中的「以后同类告警的处理方式」独立配置。两种自动方式都要求已取得 HTTP 或 systemd 异常证据，并可选择失败后站内转人工。自动动作失败、结果不确定或完成后 HTTP 仍异常时，启用了转人工的告警会进入待接手队列，人工确认后清除该标记。

## 作业库样例

```powershell
$env:DJANGO_SETTINGS_MODULE = 'opspilot_api.settings.local'
& .\.venv\Scripts\python.exe opspilot_api\manage.py seed_ops_jobs --owner <管理员账号>
```

安装 Linux 健康快照、systemd 服务状态、主机监听端口盘点、根分区容量与 inode 复核四个只读作业。安装命令可重复执行。示例作业覆盖测试、验收和其他环境，操作时仍须满足主机授权。
